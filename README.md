# 오토배틀러 (Auto Battler)

자체 세계관의 유닛을 상점에서 뽑아 헥스 보드에 배치하고, 라운드마다 AI 상대와 자동전투를 벌이는
라운드 기반 오토배틀러. 싱글 디바이스에서 플레이어 1명과 AI 봇 7명이 겨룬다.

설계 기준 문서는 프로젝트 명세서(11단계 로드맵)이며, 이 저장소는 그 로드맵을 1단계부터 순서대로 구현한다.

### UI 스택을 Compose 로 고른 이유

명세서가 XML+ViewBinding 과 Compose 중 하나를 고르고 근거를 남기라고 했다. Compose 를 골랐다.

1. **헥스 보드가 이 게임의 핵심 화면이다.** 육각형 격자는 표준 레이아웃으로 표현할 수 없어 어느 쪽을
   골라도 직접 그려야 한다. Compose 의 `Canvas` + `pointerInput` 조합이 커스텀 `View` 를 만들어
   `onDraw` / `onTouchEvent` 를 재정의하는 것보다 코드량이 적고, 드래그앤드롭(로드맵 3단계)도
   `detectDragGestures` 하나로 끝난다.
2. **전투가 100ms 틱으로 상태를 계속 갱신한다.** StateFlow 가 바뀔 때마다 알아서 다시 그려지는
   선언형 UI 가, 틱마다 어떤 View 를 어떻게 고쳐야 하는지 직접 관리하는 방식보다 버그가 적다.
3. **Kotlin 2.0 부터 Compose 컴파일러가 Kotlin 플러그인에 포함됐다.** 과거 Compose 를 어렵게 만들던
   "Kotlin 버전과 Compose 컴파일러 버전 맞추기" 문제가 사라져서 초기 세팅 비용이 거의 없다.

단점도 있다. 국내 실무에는 아직 XML 기반 레거시 코드가 많아서, XML 을 아예 안 다뤄보는 건 손해다.
다만 그건 이 프로젝트가 아니라 다른 곳에서 익히는 편이 낫다고 판단했다.

## 모듈 구조

```
autobattler/
├─ core-game/     순수 Kotlin(JVM) 모듈. 안드로이드 의존성이 전혀 없다.
│   ├─ model/         UnitDef, BoardUnit, HexCoord, PlayerState 등 도메인 모델
│   ├─ masterdata/    유닛 24, 시너지 8, 컴포넌트 9, 완성 아이템 45, 증강 10, 몬스터 4
│   ├─ economy/       상점 확률표, 공용 유닛 풀, 상점 롤, 골드/경험치 규칙
│   ├─ board/         헥스 좌표계, 화면 좌표 변환, 드래그 히트 테스트
│   ├─ combat/        틱 기반 자동전투 시뮬레이터
│   ├─ planning/      준비 단계 세션 (구매/판매/리롤/레벨업/배치)
│   └─ persistence/   Room TypeConverter 가 쓰는 인코딩 로직
└─ app/           안드로이드 모듈
    ├─ data/local/       Room 엔티티, DAO, DB, 마스터 데이터 시더
    ├─ data/repository/  GameDataRepository
    ├─ di/               Hilt 모듈
    ├─ ui/shop/          상점 화면 (Compose)
    └─ ui/board/         헥스 보드 + 벤치 캔버스, 드래그앤드롭
```

### 왜 `core-game` 을 별도 모듈로 뺐는가

명세서 6장의 레이어 구성은 `app/domain/` 아래에 전투·경제·AI 로직을 두는 그림이었다.
여기서는 그 부분을 `core-game` 이라는 **별도 Gradle 모듈**로 분리했다.

- 명세서 4-6, 9-4 가 요구하는 "UI 와 완전히 분리된 순수 Kotlin 로직 + 단위테스트 필수"를
  컴파일 단계에서 강제한다. `core-game` 에는 안드로이드 의존성이 없으므로, 실수로 `Context` 나
  `ViewModel` 을 끌어다 쓰면 빌드가 깨진다.
- 안드로이드 SDK 없이 JVM 만으로 테스트가 돌아 실행이 몇 초로 끝난다.
  전투 시뮬레이션(4단계)과 AI 스코어링(8단계)처럼 반복 실행이 많은 로직에서 차이가 크다.

패키지 이름과 레이어 경계는 명세서 6장과 같고, 물리적 위치만 다르다.

## 마스터 데이터 현황

| 항목 | 개수 | 출처 |
|---|---|---|
| 유닛 | 24종 | 명세서 4-4 원본 14종 + 확장 10종 |
| 스킬 | 24종 | 유닛 1종당 1개 |
| 시너지 | 8종 | 명세서 4-4 (계열 4 + 직업 4) |
| 아이템 컴포넌트 | 9종 | 명세서 4-5 |
| 완성 아이템 | 45종 | 컴포넌트 2개 조합의 모든 경우의 수 |
| 증강 | 10종 | 명세서 4-8 |
| 크립 몬스터 | 4종 | 명세서 4-9 |

### 로스터를 14종에서 24종으로 늘린 이유

명세서 4-4 는 계열 시너지 임계값을 2/4/6 으로 정했는데, 원본 로스터 14종은 계열별로 3~4종뿐이라
임계값 6 을 어느 계열도 달성할 수 없었다. 직업도 수호자/사수가 3종뿐이라 임계값 4 가 막혀 있었다.
그대로 두면 5단계 시너지 엔진의 절반이 죽은 코드가 되므로 **계열 6종 / 직업 6종**이 되도록 10종을 추가했다.

| | 검사 | 마법사 | 사수 | 수호자 | 합계 |
|---|---|---|---|---|---|
| 기계공학자 | 2 | 1 | 2 | 1 | 6 |
| 심연의 아이들 | 2 | 2 | 1 | 1 | 6 |
| 황금가문 | 1 | 1 | 2 | 2 | 6 |
| 폭풍의 부족 | 1 | 2 | 1 | 2 | 6 |
| 합계 | 6 | 6 | 6 | 6 | 24 |

명세서 원본 14종은 `SPEC_UNIT_DEFS` 에, 추가한 10종은 `EXPANSION_UNIT_DEFS` 에 따로 두었다.
원본의 스탯은 명세서 확정값이므로 수정하지 않는다.

코스트 분포는 1코스트 6종, 2코스트 6종, 3코스트 5종, 4코스트 4종, 5코스트 3종이다.

### 완성 아이템 45종

명세서 4-5 는 "3x3=9칸 조합 매트릭스"라고 적었지만 컴포넌트가 9종이므로 실제 격자는 9x9 이고,
순서를 무시한 조합의 수는 9 x 10 / 2 = **45가지**다. 원작 구성을 참고해 45칸을 모두 채웠다.
이름과 표현은 자체 창작이다.

완성 아이템의 스탯은 **재료 컴포넌트 2개의 스탯 합으로 자동 계산**한다. 45벌을 손으로 적지 않으므로
재료만 바꾸고 스탯표를 안 고치는 종류의 실수가 생기지 않는다. 고유 효과는 `effectId` 로만 정의해
두었고, 실제 효과 구현은 로드맵 7단계에서 붙인다.

## 임의 초기값으로 채운 항목

명세서에 수치가 없어 임의로 정한 값이다. 로드맵 11단계 밸런스 튜닝에서 조정한다.

- 유닛의 `attackSpeed` (명세서 4-4 표에 열이 없음)
- 유닛 판매가 규칙 (명세서 4-1 에 판매 언급만 있고 가격이 없음)
- 확장 유닛 10종의 모든 스탯 (명세서에 없는 유닛)
- 스킬의 마나 비용 / 시작 마나 / 기본 위력 / 범위 (명세서 4-6 이 임의값으로 채우라고 명시)
- 아이템 컴포넌트의 스탯 증가량 (명세서 4-5 는 이름만 정의)
- 완성 아이템의 고유 효과 수치 (문구만 정의, 수치는 7단계에서)
- 연승·연패 보너스 골드 표, 라운드당 자동 지급 경험치 (명세서 4-1, 4-2 에 수치 없음)
- 벤치 칸 수 9칸, 시작 체력 100
- 보드 크기 7칸 x 4줄 (명세서 4-6 에 크기 규정 없음)
- 전투의 마나 획득량, 이동 간격, 최대 전투 시간, 패배 시 체력 손실량 (명세서 4-6 은 틱 100ms 만 정함)

## 2단계에서 정한 규칙

### 판매가

명세서 4-1 은 판매를 언급만 하고 가격을 정하지 않아 원작 관행을 따랐다. 11단계에서 조정한다.

- 1코스트는 성 등급과 무관하게 산 값 그대로 돌려받는다 (1 / 3 / 9골드)
- 2코스트 이상은 2성부터 1골드씩 손해를 본다 (`코스트 x 3 - 1`, `코스트 x 9 - 1`)

판매하면 그 유닛이 소모한 카드가 전부 공용 풀로 돌아간다. 2성은 3장, 3성은 9장이다.

### 카드 총량 보존

상점에 뜬 유닛은 그 순간 이미 풀에서 빠진 상태다. 따라서

- **구매**는 풀을 건드리지 않는다. 카드가 상점에서 벤치로 옮겨갈 뿐이다.
- **리롤**은 아직 사지 않은 칸만 풀에 되돌린다. 산 칸은 벤치에 있으므로 되돌리지 않는다.
- **판매**할 때 비로소 카드가 풀로 돌아간다.

`풀에 남은 장수 + 상점에 떠 있는 장수 + 플레이어가 가진 장수`의 합은 어떤 조작을 해도 변하지 않으며,
`PlanningSessionTest.카드 총량은 어떤 조작에도 변하지 않는다` 가 이를 검증한다.
8인이 재고를 공유하는 구조라 이 불변식이 깨지면 경제 전체가 무너진다.

## 3단계에서 정한 규칙

### 헥스 좌표계

육각형 격자를 (행, 열)로 다루면 이웃 계산이 지저분해진다. 그래서 저장과 계산은 전부
**axial 좌표** (q, r)로 한다. 세 번째 축 s 는 `q + r + s = 0` 으로 유도되므로 저장하지 않는다.
거리는 세 축 차이의 절댓값 합을 2로 나눈 값이고, 이웃은 여섯 방향 벡터를 더하면 된다.
사람이 읽는 "몇 번째 줄 몇 번째 칸"이 필요할 때만 `OffsetCoord` 로 변환한다.

보드는 가로 7칸 x 세로 4줄, 총 28칸이다. 명세서에 크기 규정이 없어 원작 관행을 따랐다.
홀수 줄이 반 칸 오른쪽으로 밀리는 odd-r 배치다.

보드에 올릴 수 있는 유닛 수는 플레이어 레벨과 같다.

### 드래그앤드롭을 테스트 가능하게 만든 방법

드래그앤드롭에서 가장 틀리기 쉬운 부분은 "손가락이 놓인 지점이 어느 칸인가"다.
이 계산이 어긋나면 화면상으로는 멀쩡해 보여도 엉뚱한 칸에 유닛이 놓이고,
에뮬레이터로는 찾기 어렵다.

그래서 보드와 벤치를 **하나의 좌표계**(`PlayfieldLayout`)로 배치하고, 픽셀 → 칸 변환과
히트 테스트를 안드로이드 의존성 없는 `core-game` 에 두었다. Compose 쪽은 그 결과를 그리고
터치 좌표를 넘기기만 한다. 덕분에 28칸 전체에 대해 "중심을 누르면 그 칸이 나오는지",
"보드를 촘촘히 훑었을 때 항상 가장 가까운 칸이 나오는지"를 단위테스트로 검증할 수 있다.

픽셀 → axial 변환은 단순 반올림으로는 안 된다. 세 축의 합이 0이어야 한다는 제약이 깨져
엉뚱한 칸이 나오기 때문에, 오차가 가장 큰 축을 나머지 둘로부터 다시 계산하는
cube 반올림을 쓴다.

### 배치 규칙

- 빈 칸으로 옮길 때만 보드 정원을 확인한다.
- 이미 유닛이 있는 칸으로 옮기면 **두 유닛이 자리를 맞바꾼다.** 정원이 변하지 않으므로
  보드가 꽉 찬 상태에서도 벤치 유닛과 보드 유닛을 교체할 수 있다.
- 벤치 영역에 떨어뜨리면 회수된다. 벤치가 꽉 차 있으면 실패하고 보드에 그대로 남는다.
- 판매는 드래그가 아니라 탭으로 고른 뒤 버튼을 누른다. 옮기다가 실수로 파는 일을 막기 위해서다.

### ShopSession 을 PlanningSession 으로 바꾼 이유

2단계에서 만든 `ShopSession` 이 3단계부터 보드 배치까지 맡게 됐다. 상점만 다루지 않으므로
명세서 3장의 용어를 따라 `PlanningSession`(준비 단계)으로 이름을 바꾸고
`core-game/planning` 패키지로 옮겼다. 상점 확률표와 유닛 풀은 `economy` 에 그대로 남아 있다.

### 아직 붙이지 않은 것

- 같은 유닛 3개를 사도 자동 합성되지 않는다. 합성은 로드맵 6단계다.
- 보드에 올려도 시너지가 적용되지 않는다. 시너지 엔진은 로드맵 5단계다.
- "다음 라운드" 버튼은 수입만 지급한다. 전투 엔진은 4단계에서 만들었지만
  상대할 AI 봇 구성이 8단계에 있어 아직 화면에 연결하지 않았다.

## 4단계에서 정한 규칙

### 전장은 배치 보드 두 개를 맞붙인 7칸 x 8줄이다

배치 보드는 7x4 인데 전투는 두 진영이 마주 봐야 하므로, 같은 보드를 위아래로 붙인 7x8 전장을 쓴다.
적이 위쪽 0~3줄, 플레이어가 아래쪽 4~7줄이다. 각자의 배치 보드에서는 **아래쪽 줄이 최전방**이므로
플레이어 쪽만 위아래를 뒤집어 옮긴다. 그래야 양쪽의 3번 줄(최전방)이 전장 한가운데에서 맞닿는다.

크기가 다른 두 격자가 같은 계산을 쓰도록 좌표 로직을 `HexGrid(rows, columns)` 로 일반화했고,
`HexBoard` 는 7x4 인스턴스를 감싸는 얇은 껍데기가 됐다. 4줄에서만 맞고 8줄에서 틀리는 계산이
생기지 않도록 `HexGridTest` 가 여러 크기에서 같은 성질을 검증한다.

### 틱마다 유닛 1기가 하는 일

100ms 틱마다 살아 있는 모든 유닛이 한 번씩 행동한다. 대상은 항상 **가장 가까운 적**이고,
우선순위는 다음과 같다.

1. 사거리 안이고 마나가 가득 찼으면 **스킬**
2. 사거리 안이고 공격 대기가 끝났으면 **기본 공격**
3. 사거리 밖이면 **한 칸 이동**

이동은 "대상을 때릴 수 있는 칸"들을 출발점으로 삼아 BFS(너비 우선 탐색: 가까운 칸부터 차례로
퍼져 나가며 최단 거리를 재는 방법)를 한 번 돌리고, 지금 위치보다 가까워지는 이웃 칸으로 한 칸 간다.
목표 쪽에서 거꾸로 퍼뜨리므로 유닛마다 경로 탐색을 새로 돌리지 않아도 된다.

마나는 공격할 때 10, 맞을 때 5 씩 찬다. 스킬을 쓰면 0으로 비운다. 전부 임의 초기값이다.

### 난수를 전혀 쓰지 않는다

행동 순서는 유닛 id 순으로 고정하고, 거리가 같은 후보가 여럿이면 id 순, 갈 수 있는 칸이 여럿이면
전장 좌표 순서로 고른다. 그래서 같은 배치를 넣으면 언제나 같은 결과가 나온다.

이렇게 한 이유는 두 가지다. 첫째, 결과가 고정되지 않으면 "몇 틱에 누가 죽는가"를 단위테스트로
검증할 수 없다. 둘째, 한 라운드에 8명의 전투가 동시에 돌아가는 구조에서 재현되지 않는 버그가
생기면 원인을 찾을 수 없다. 치명타 같은 확률 요소는 11단계에서 붙인다.

### 무승부와 시간 초과

3000틱(300초)이 지나면 강제로 끊고, 남은 체력 총합이 많은 쪽이 이긴다. 그것도 같으면 무승부다.
서로 닿지 못하거나 회복량이 피해량을 넘는 구성에서 전투가 끝나지 않는 것을 막기 위해서다.

### 3성 스탯을 반올림으로 바꿨다

`1.8f` 는 이진 부동소수로 정확히 표현되지 않아 `1.8f * 1.8f` 가 3.2399998 이 된다.
버림으로 계산하면 명세서 4-3 의 3.24배가 어긋나 3성 체력 3240 이 3239 가 된다.
`BoardUnit` 과 `CombatUnit` 의 스탯 계산을 전부 반올림으로 바꿨고, 두 값이 어긋나지 않는지
`CombatUnitTest.3성 스탯은 버림 오차 없이 3점24배다` 가 검증한다.

### 4단계에서 아직 반영하지 않은 것

- **방어력 / 마법저항이 없다.** 명세서 4-4 로스터 표에 해당 열이 없어 피해가 그대로 들어간다.
- **스킬은 피해형 1종만 구현했다.** 명세서 4-6 이 요구한 "스킬 1종"에 맞춘 것으로,
  회복이나 도발 같은 다른 종류는 이름만 있고 동작은 피해로 처리된다. 종류별 분기는 이후 단계다.
- 시너지 버프는 5단계, 아이템 효과는 7단계에서 이 계산에 끼워 넣는다.
- 전투 화면과 애니메이션은 10단계다. 지금은 `CombatOutcome.events` 에 일어난 일이 순서대로
  쌓이므로, 10단계에서 그 목록을 재생하기만 하면 된다.
