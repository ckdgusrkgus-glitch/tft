# 오토배틀러 (Auto Battler)

자체 세계관의 유닛을 상점에서 뽑아 헥스 보드에 배치하고, 라운드마다 AI 상대와 자동전투를 벌이는
라운드 기반 오토배틀러. 싱글 디바이스에서 플레이어 1명과 AI 봇 7명이 겨룬다.

설계 기준 문서는 프로젝트 명세서(11단계 로드맵)이며, 이 저장소는 그 로드맵을 1단계부터 순서대로 구현한다.

### JDK 는 17~21 을 써야 한다

Gradle 8.11.1 은 **자바 23 까지만** 그 위에서 돌 수 있다. 자바 24 는 Gradle 8.14, 자바 25 는
Gradle 9.1.0 이 필요하다. ([Gradle 호환성 표](https://docs.gradle.org/current/userguide/compatibility.html))

최근 안드로이드 스튜디오는 자바 25 기반 JBR 을 번들한다. 그대로 두면 빌드가 이렇게 깨진다.

```
* What went wrong:
25.0.2
```

원인 줄이 하나도 없어 메시지만 보고는 알 수 없다. 그래서 `settings.gradle.kts` 가 빌드 시작 전에
JDK 버전을 먼저 확인하고 무엇을 고쳐야 하는지 알려 준다.

고치는 법은 두 군데를 따로 봐야 한다. **안드로이드 스튜디오의 Gradle JDK 설정은 터미널에 적용되지 않는다.**

| 어디서 빌드하나 | 어디를 바꾸나 |
|---|---|
| 안드로이드 스튜디오 | Settings > Build, Execution, Deployment > Build Tools > Gradle > **Gradle JDK** 에서 21 선택. 없으면 같은 자리의 `Download JDK...` 로 받는다 |
| 터미널 `./gradlew` | 사용자 홈의 `.gradle/gradle.properties` 에 `org.gradle.java.home` 을 적거나 `JAVA_HOME` 을 바꾼다 |

바꾼 뒤에는 `./gradlew --stop` 으로 옛 데몬을 내린다.

## 기술 스택

| 영역 | 선택 |
|---|---|
| 언어 | Kotlin |
| UI | Jetpack Compose (선택 근거는 아래 참고) |
| 아키텍처 | MVVM (ViewModel + StateFlow) |
| DI | Hilt |
| 로컬 저장소 | Room |
| 비동기 | Coroutine + Flow |
| 테스트 | JUnit4, Turbine, Robolectric |

### UI 스택을 Compose 로 고른 이유

명세서가 XML+ViewBinding 과 Compose 중 하나를 고르고 근거를 남기라고 했다. Compose 를 골랐다.

1. **헥스 보드가 이 게임의 핵심 화면이다.** 육각형 격자는 표준 레이아웃으로 표현할 수 없어 어느 쪽을
   골라도 직접 그려야 한다. Compose 의 `Canvas` + `pointerInput` 조합이 커스텀 `View` 를 만들어
   `onDraw` / `onTouchEvent` 를 재정의하는 것보다 코드량이 적고, 드래그앤드롭(로드맵 3단계)도
   `detectDragGestures` 하나로 끝난다.
2. **전투가 100ms 틱으로 상태를 계속 갱신한다.** StateFlow 가 바뀔 때마다 알아서 다시 그려지는
   선언형 UI 가, 틱마다 어떤 View 를 어떻게 고쳐야 하는지 직접 관리하는 방식보다 버그가 적다.
3. **Kotlin 2.0 부터 Compose 컴파일러가 Kotlin 플러그인에 포함됐다.** 과거 Compose 를 어렵게 만들던
   "Kotlin 버전과 Compose 컴파일러 버전 맞추기" 문제가 사라져서 초기 세팅 비용이 거의 없다.

단점도 있다. 국내 실무에는 아직 XML 기반 레거시 코드가 많아서, XML 을 아예 안 다뤄보는 건 손해다.
다만 그건 이 프로젝트가 아니라 다른 곳에서 익히는 편이 낫다고 판단했다.

│   ├─ economy/       상점 확률표, 공용 유닛 풀, 상점 롤, 골드/경험치 규칙
│   ├─ board/         헥스 좌표계, 화면 좌표 변환, 드래그 히트 테스트

│   └─ persistence/   Room TypeConverter 가 쓰는 인코딩 로직

    ├─ data/repository/  GameDataRepository

    ├─ ui/shop/          상점 화면 + 시너지 패널 (Compose)

### 왜 `core-game` 을 별도 모듈로 뺐는가

명세서 6장의 레이어 구성은 `app/domain/` 아래에 전투·경제·AI 로직을 두는 그림이었다.
여기서는 그 부분을 `core-game` 이라는 **별도 Gradle 모듈**로 분리했다.

- 명세서 4-6, 9-4 가 요구하는 "UI 와 완전히 분리된 순수 Kotlin 로직 + 단위테스트 필수"를
  컴파일 단계에서 강제한다. `core-game` 에는 안드로이드 의존성이 없으므로, 실수로 `Context` 나
  `ViewModel` 을 끌어다 쓰면 빌드가 깨진다.
- 안드로이드 SDK 없이 JVM 만으로 테스트가 돌아 실행이 몇 초로 끝난다.
  전투 시뮬레이션(4단계)과 AI 스코어링(8단계)처럼 반복 실행이 많은 로직에서 차이가 크다.

패키지 이름과 레이어 경계는 명세서 6장과 같고, 물리적 위치만 다르다.

### 로스터를 14종에서 24종으로 늘린 이유

명세서 4-4 는 계열 시너지 임계값을 2/4/6 으로 정했는데, 원본 로스터 14종은 계열별로 3~4종뿐이라
임계값 6 을 어느 계열도 달성할 수 없었다. 직업도 수호자/사수가 3종뿐이라 임계값 4 가 막혀 있었다.
그대로 두면 5단계 시너지 엔진의 절반이 죽은 코드가 되므로 **계열 6종 / 직업 6종**이 되도록 10종을 추가했다.

| | 검사 | 마법사 | 사수 | 수호자 | 합계 |
|---|---|---|---|---|---|
| 기계공학자 | 2 | 1 | 2 | 1 | 6 |
| 심연의 아이들 | 2 | 2 | 1 | 1 | 6 |
| 황금가문 | 1 | 1 | 2 | 2 | 6 |
| 폭풍의 부족 | 1 | 2 | 1 | 2 | 6 |
| 합계 | 6 | 6 | 6 | 6 | 24 |

명세서 원본 14종은 `SPEC_UNIT_DEFS` 에, 추가한 10종은 `EXPANSION_UNIT_DEFS` 에 따로 두었다.
원본의 스탯은 명세서 확정값이므로 수정하지 않는다.

코스트 분포는 1코스트 6종, 2코스트 6종, 3코스트 5종, 4코스트 4종, 5코스트 3종이다.

### 완성 아이템 45종

명세서 4-5 는 "3x3=9칸 조합 매트릭스"라고 적었지만 컴포넌트가 9종이므로 실제 격자는 9x9 이고,
순서를 무시한 조합의 수는 9 x 10 / 2 = **45가지**다. 원작 구성을 참고해 45칸을 모두 채웠다.
이름과 표현은 자체 창작이다.

완성 아이템의 스탯은 **재료 컴포넌트 2개의 스탯 합으로 자동 계산**한다. 45벌을 손으로 적지 않으므로
재료만 바꾸고 스탯표를 안 고치는 종류의 실수가 생기지 않는다. 고유 효과는 `effectId` 로만 정의해
두었고, **실제 효과 구현은 아직 없다.** 7단계는 스탯 합산까지만 했다. 이유는 아래 7단계 항목에 적었다.

## 임의 초기값으로 채운 항목

명세서에 수치가 없어 임의로 정한 값이다. 로드맵 11단계 밸런스 튜닝에서 조정한다.

- 유닛의 `attackSpeed` (명세서 4-4 표에 열이 없음)
- 유닛 판매가 규칙 (명세서 4-1 에 판매 언급만 있고 가격이 없음)
- 확장 유닛 10종의 모든 스탯 (명세서에 없는 유닛)
- 스킬의 마나 비용 / 시작 마나 / 기본 위력 / 범위 (명세서 4-6 이 임의값으로 채우라고 명시)
- 아이템 컴포넌트의 스탯 증가량 (명세서 4-5 는 이름만 정의)
- 완성 아이템의 고유 효과 수치 (문구만 정의, 수치는 11단계에서)
- 연승·연패 보너스 골드 표, 라운드당 자동 지급 경험치 (명세서 4-1, 4-2 에 수치 없음)
- 벤치 칸 수 9칸, 시작 체력 100
- 보드 크기 7칸 x 4줄 (명세서 4-6 에 크기 규정 없음)
- 전투의 마나 획득량, 이동 간격, 최대 전투 시간, 패배 시 체력 손실량 (명세서 4-6 은 틱 100ms 만 정함)
- 시너지 8종의 단계별 실제 수치 전부 (명세서 4-4 는 "공격력 증가"처럼 방향만 적었다) — `synergy/SynergyTables`
- 방어력 점수를 피해 감소로 바꾸는 공식과 상수 (명세서에 공식이 없다)

## 2단계에서 정한 규칙

### 판매가

명세서 4-1 은 판매를 언급만 하고 가격을 정하지 않아 원작 관행을 따랐다. 11단계에서 조정한다.

- 1코스트는 성 등급과 무관하게 산 값 그대로 돌려받는다 (1 / 3 / 9골드)
- 2코스트 이상은 2성부터 1골드씩 손해를 본다 (`코스트 x 3 - 1`, `코스트 x 9 - 1`)

판매하면 그 유닛이 소모한 카드가 전부 공용 풀로 돌아간다. 2성은 3장, 3성은 9장이다.

### 카드 총량 보존

상점에 뜬 유닛은 그 순간 이미 풀에서 빠진 상태다. 따라서

- **구매**는 풀을 건드리지 않는다. 카드가 상점에서 벤치로 옮겨갈 뿐이다.
- **리롤**은 아직 사지 않은 칸만 풀에 되돌린다. 산 칸은 벤치에 있으므로 되돌리지 않는다.
- **판매**할 때 비로소 카드가 풀로 돌아간다.

`풀에 남은 장수 + 상점에 떠 있는 장수 + 플레이어가 가진 장수`의 합은 어떤 조작을 해도 변하지 않으며,
`PlanningSessionTest.카드 총량은 어떤 조작에도 변하지 않는다` 가 이를 검증한다.
8인이 재고를 공유하는 구조라 이 불변식이 깨지면 경제 전체가 무너진다.

## 3단계에서 정한 규칙

### 헥스 좌표계

육각형 격자를 (행, 열)로 다루면 이웃 계산이 지저분해진다. 그래서 저장과 계산은 전부
**axial 좌표** (q, r)로 한다. 세 번째 축 s 는 `q + r + s = 0` 으로 유도되므로 저장하지 않는다.
거리는 세 축 차이의 절댓값 합을 2로 나눈 값이고, 이웃은 여섯 방향 벡터를 더하면 된다.
사람이 읽는 "몇 번째 줄 몇 번째 칸"이 필요할 때만 `OffsetCoord` 로 변환한다.

보드는 가로 7칸 x 세로 4줄, 총 28칸이다. 명세서에 크기 규정이 없어 원작 관행을 따랐다.
홀수 줄이 반 칸 오른쪽으로 밀리는 odd-r 배치다.

보드에 올릴 수 있는 유닛 수는 플레이어 레벨과 같다.

### 드래그앤드롭을 테스트 가능하게 만든 방법

드래그앤드롭에서 가장 틀리기 쉬운 부분은 "손가락이 놓인 지점이 어느 칸인가"다.
이 계산이 어긋나면 화면상으로는 멀쩡해 보여도 엉뚱한 칸에 유닛이 놓이고,
에뮬레이터로는 찾기 어렵다.

그래서 보드와 벤치를 **하나의 좌표계**(`PlayfieldLayout`)로 배치하고, 픽셀 → 칸 변환과
히트 테스트를 안드로이드 의존성 없는 `core-game` 에 두었다. Compose 쪽은 그 결과를 그리고
터치 좌표를 넘기기만 한다. 덕분에 28칸 전체에 대해 "중심을 누르면 그 칸이 나오는지",
"보드를 촘촘히 훑었을 때 항상 가장 가까운 칸이 나오는지"를 단위테스트로 검증할 수 있다.

픽셀 → axial 변환은 단순 반올림으로는 안 된다. 세 축의 합이 0이어야 한다는 제약이 깨져
엉뚱한 칸이 나오기 때문에, 오차가 가장 큰 축을 나머지 둘로부터 다시 계산하는
cube 반올림을 쓴다.

### 배치 규칙

- 빈 칸으로 옮길 때만 보드 정원을 확인한다.
- 이미 유닛이 있는 칸으로 옮기면 **두 유닛이 자리를 맞바꾼다.** 정원이 변하지 않으므로
  보드가 꽉 찬 상태에서도 벤치 유닛과 보드 유닛을 교체할 수 있다.
- 벤치 영역에 떨어뜨리면 회수된다. 벤치가 꽉 차 있으면 실패하고 보드에 그대로 남는다.
- 판매는 드래그가 아니라 탭으로 고른 뒤 버튼을 누른다. 옮기다가 실수로 파는 일을 막기 위해서다.

### ShopSession 을 PlanningSession 으로 바꾼 이유

2단계에서 만든 `ShopSession` 이 3단계부터 보드 배치까지 맡게 됐다. 상점만 다루지 않으므로
명세서 3장의 용어를 따라 `PlanningSession`(준비 단계)으로 이름을 바꾸고
`core-game/planning` 패키지로 옮겼다. 상점 확률표와 유닛 풀은 `economy` 에 그대로 남아 있다.

### 아직 붙이지 않은 것

- 같은 유닛 3개를 사도 자동 합성되지 않는다. 합성은 로드맵 6단계다.
- "다음 라운드" 버튼은 수입만 지급한다. 전투 엔진은 4단계에서 만들었지만
  상대할 AI 봇 구성이 8단계에 있어 아직 화면에 연결하지 않았다.

## 4단계에서 정한 규칙

### 전장은 배치 보드 두 개를 맞붙인 7칸 x 8줄이다

배치 보드는 7x4 인데 전투는 두 진영이 마주 봐야 하므로, 같은 보드를 위아래로 붙인 7x8 전장을 쓴다.
적이 위쪽 0~3줄, 플레이어가 아래쪽 4~7줄이다. 각자의 배치 보드에서는 **아래쪽 줄이 최전방**이므로
플레이어 쪽만 위아래를 뒤집어 옮긴다. 그래야 양쪽의 3번 줄(최전방)이 전장 한가운데에서 맞닿는다.

크기가 다른 두 격자가 같은 계산을 쓰도록 좌표 로직을 `HexGrid(rows, columns)` 로 일반화했고,
`HexBoard` 는 7x4 인스턴스를 감싸는 얇은 껍데기가 됐다. 4줄에서만 맞고 8줄에서 틀리는 계산이
생기지 않도록 `HexGridTest` 가 여러 크기에서 같은 성질을 검증한다.

### 틱마다 유닛 1기가 하는 일

100ms 틱마다 살아 있는 모든 유닛이 한 번씩 행동한다. 대상은 항상 **가장 가까운 적**이고,
우선순위는 다음과 같다.

1. 사거리 안이고 마나가 가득 찼으면 **스킬**
2. 사거리 안이고 공격 대기가 끝났으면 **기본 공격**
3. 사거리 밖이면 **한 칸 이동**

이동은 "대상을 때릴 수 있는 칸"들을 출발점으로 삼아 BFS(너비 우선 탐색: 가까운 칸부터 차례로
퍼져 나가며 최단 거리를 재는 방법)를 한 번 돌리고, 지금 위치보다 가까워지는 이웃 칸으로 한 칸 간다.
목표 쪽에서 거꾸로 퍼뜨리므로 유닛마다 경로 탐색을 새로 돌리지 않아도 된다.

마나는 공격할 때 10, 맞을 때 5 씩 찬다. 스킬을 쓰면 0으로 비운다. 전부 임의 초기값이다.

### 난수를 전혀 쓰지 않는다

행동 순서는 유닛 id 순으로 고정하고, 거리가 같은 후보가 여럿이면 id 순, 갈 수 있는 칸이 여럿이면
전장 좌표 순서로 고른다. 그래서 같은 배치를 넣으면 언제나 같은 결과가 나온다.

이렇게 한 이유는 두 가지다. 첫째, 결과가 고정되지 않으면 "몇 틱에 누가 죽는가"를 단위테스트로
검증할 수 없다. 둘째, 한 라운드에 8명의 전투가 동시에 돌아가는 구조에서 재현되지 않는 버그가
생기면 원인을 찾을 수 없다. 치명타 같은 확률 요소는 11단계에서 붙인다.

### 무승부와 시간 초과

3000틱(300초)이 지나면 강제로 끊고, 남은 체력 총합이 많은 쪽이 이긴다. 그것도 같으면 무승부다.
서로 닿지 못하거나 회복량이 피해량을 넘는 구성에서 전투가 끝나지 않는 것을 막기 위해서다.

### 3성 스탯을 반올림으로 바꿨다

`1.8f` 는 이진 부동소수로 정확히 표현되지 않아 `1.8f * 1.8f` 가 3.2399998 이 된다.
버림으로 계산하면 명세서 4-3 의 3.24배가 어긋나 3성 체력 3240 이 3239 가 된다.
`BoardUnit` 과 `CombatUnit` 의 스탯 계산을 전부 반올림으로 바꿨고, 두 값이 어긋나지 않는지
`CombatUnitTest.3성 스탯은 버림 오차 없이 3점24배다` 가 검증한다.

### 4단계에서 아직 반영하지 않은 것

- **방어력 / 마법저항이 없다.** 명세서 4-4 로스터 표에 해당 열이 없어 피해가 그대로 들어간다.
- **스킬은 피해형 1종만 구현했다.** 명세서 4-6 이 요구한 "스킬 1종"에 맞춘 것으로,
  회복이나 도발 같은 다른 종류는 이름만 있고 동작은 피해로 처리된다. 종류별 분기는 이후 단계다.
- 시너지 버프는 5단계, 아이템 효과는 7단계에서 이 계산에 끼워 넣는다.
- 전투 화면과 애니메이션은 10단계다. 지금은 `CombatOutcome.events` 에 일어난 일이 순서대로
  쌓이므로, 10단계에서 그 목록을 재생하기만 하면 된다.

## 5단계에서 정한 규칙

### 시너지 인원은 "몇 종"이지 "몇 개"가 아니다

강철수호병을 세 장 올려도 기계공학자 1명, 수호자 1명이다. 보드 위 **서로 다른 유닛 종류**만 센다.

명세서 4-4 는 열 제목을 "임계값(인원)"이라고만 적고 복제본 처리를 한 글자도 말하지 않는다.
**확정값이 아니라 해석**이고 근거는 넷이다.

1. 보드에 올릴 수 있는 수가 레벨과 같아 최대 10칸인데, 개수를 세면 1코스트 유닛 세 장으로
   계열 3을 3골드에 사게 되어 2/4/6 사다리가 무너진다.
2. 로스터를 24종으로 늘린 이유 자체가 계열 6종·직업 6종을 맞추기 위해서였다. 개수를 센다면
   그 작업이 불필요했다.
3. 명세서 4-7 의 AI 스코어링이 복제본("이미 보유한 동일 유닛 개수")과 태그 겹침을 **서로 다른 항**으로
   가격 매긴다. 복제본은 스타업 가치, 태그는 시너지 가치다.
4. 6단계 자동 합성이 같은 성급 복제본을 없애므로, 개수 기준 집계는 과도기에만 보이는 불안정한 규칙이다.

11단계 재검토 대상으로 표시해 두었다.

### 명세서와 엔진이 부딪친 곳 네 군데

| 시너지 | 명세서 문구 | 문제 | 5단계의 답 |
|---|---|---|---|
| 기계공학자 | 방어력/마법저항력 증가 | 그 스탯이 데이터 모델에 없다 | 로스터 표는 건드리지 않고 전투 유닛에만 방어력 점수를 둔다 |
| 기계공학자 6인 | 거대 골렘 소환 | 소환할 유닛도, 전투 중 합류 경로도 없다 | 명세만 내보내고 소환은 10단계로 미룬다 |
| 심연의 아이들 | 주기적으로 쉴드 | 쉴드 개념이 없다 | 체력과 분리된 쉴드 필드와 주기 갱신 단계를 만든다 |
| 폭풍의 부족 | 일정 확률로 연쇄 번개 | 전투가 난수를 전혀 쓰지 않는다 | 확률을 정수 누적 충전으로 옮긴다 |

### 확률을 난수 없이 구현한 방법

명세서에서 확률을 요구하는 효과는 폭풍의 부족 하나뿐이다. 그런데 4단계에서 "난수를 전혀 쓰지
않는다"고 정해 뒀고, 그게 "몇 틱에 누가 죽는가"를 단위테스트로 고정하는 근거다. 난수를 넣으면
기존 전투 테스트가 통째로 의미를 잃는다.

그래서 **정수 누적 충전**으로 옮겼다. 기본 공격마다 단계별 충전량(20 / 35 / 50)을 쌓고 100을
넘으면 연쇄 번개가 터진 뒤 100을 뺀다. 명세서의 확률 숫자가 충전량으로 그대로 보존되므로
11단계는 확률을 튜닝하듯 같은 손잡이를 돌리면 된다.

- 기대 발동 빈도가 확률과 같고 분산만 0이다.
- M번 공격하면 발동 횟수가 정확히 `M x 충전량 / 100` 이라, 11단계가 수치를 어떻게 바꿔도
  성립하는 식으로 단언할 수 있다. "N번째 공격마다"는 35% 같은 값을 표현하지 못하고,
  시드 난수는 테스트가 해시 구현에 묶인다.

### 방어력은 퍼센트가 아니라 점수다

퍼센트는 더해지지 않는다. 50% 감소 둘을 더하면 100%가 되어 무적이 된다. 점수는 더해진다.

기계공학자(5단계), 수호의흔장/저항의흔장(7단계), 강철의의지(9단계)가 전부 하나의 방어력 점수에
쏟아져 들어가고, 점수를 감소율로 바꾸는 변환은 `CombatRules.damageAfterArmor` 한 곳에서만 한다.
`피해 x 100 / (100 + 방어력)` 정수 나눗셈이라 피해 경로에 부동소수가 없고, 수익 체감이라
뺄셈식처럼 공격력 낮은 유닛을 완전히 무력화하는 절벽이 없다.

방어력과 마법저항력은 5단계에서 한 풀로 합쳤다. 기계공학자가 둘을 항상 함께 올리고 피해에
종류 구분이 없어 어떤 테스트도 둘을 구별할 수 없기 때문이다. 7단계에서 나눈다.

### 시너지를 combat 이 아니라 별도 패키지에 둔 이유

황금가문만 전투가 아니라 경제에 붙는다. 시너지 엔진을 "전투 유닛에 버프를 바르는 함수"로
설계하면 황금가문이 들어갈 자리가 없고, 억지로 끼우면 economy 가 combat 을 의존하게 된다.

그래서 `SynergyEngine.resolve(board)` 는 보드만 받아 해석 결과 하나를 돌려주고, 전투·경제·화면
셋이 서로를 모른 채 각자 필요한 부분만 읽는다. 명세서 6장이 `synergy/` 를 `combat/` 의 형제로
둔 구성과 같다. 8단계 AI 스코어링도 `resolve(보드 + 후보유닛)` 으로 가상 보드를 그대로 물어볼 수 있다.

### 실제로 돌려본 결과

완전히 같은 보드(기계공학자 6종) 둘을 붙이고 아군에게만 시너지를 적용하면

```
시너지 없음  -> 적군 승리  72틱  아군 생존 0기
시너지 적용  -> 아군 승리  69틱  아군 생존 4기
```

### 5단계에서 아직 반영하지 않은 것

- **거대 골렘을 실제로 소환하지 않는다.** 기계공학자 6단계는 소환 명세만 내보내고, 테스트가
  "명세는 나오지만 전투 유닛 수는 늘지 않는다"를 단언해 이 보류가 잊히지 않게 한다.
  10단계 PvE 몬스터가 "스킬 없이 기본 공격만 하는 개체"라는 똑같은 기능을 요구하므로 거기서 한 번에 만든다.
- 방어력과 마법저항력이 나뉘지 않는다. 7단계에서 피해 종류를 도입하며 쪼갠다.
- 황금가문 골드는 라운드 **시작**에 정산된다. 전투가 끝난 뒤 다음 라운드 시작 사이에 보드를
  건드리는 코드가 없어 금액은 같다. 진짜 라운드 종료 훅은 9단계 증강이 실제로 요구할 때 만든다.
- 공격속도 버프는 정수 틱 단위라 해상도가 거칠다. 그래서 사수 시너지 수치를 로스터 6종 전부의
  공격 간격이 실제로 줄어드는 값으로 골랐고, 전수 테스트가 그것을 지킨다.

## 6단계에서 정한 규칙

명세서 4-3 이 정한 것은 두 줄뿐이다. 같은 유닛 3개면 2성, 2성 3개(= 1성 9장)면 3성.
나머지는 전부 아래처럼 해석했고 11단계 재검토 대상이다.

### 벤치와 보드를 함께 센다

한쪽만 보면 "벤치에 2개, 보드에 1개"가 영원히 합성되지 않는다. 명세서에 범위 제한이 없다.

### 어느 3개를 먹고 누가 살아남는가

같은 유닛이 4개 이상일 수 있으므로 **소모 순서**가 필요하고, 난수를 쓰지 않으므로 고정해야 한다.

| 정한 것 | 값 | 이유 |
|---|---|---|
| 소모 순서 | 벤치 먼저, 그 다음 보드 (각 목록 순서대로) | 보드를 먼저 먹으면 배치해 둔 진형이 임의로 무너진다 |
| 살아남는 개체 | 소모된 셋 중 보드에 있던 첫 유닛, 셋 다 벤치면 첫 벤치 유닛 | 보드 자리를 지켜야 진형이 유지된다 |
| 물려받는 것 | `instanceId` 와 `position` | 화면의 선택 상태와 좌표가 그대로 남는다 |

보드 유닛 2개가 한 번에 먹히면 보드 인원이 하나 줄지만 **늘어나는 일은 없어** 정원을 넘길 수 없다.

### 풀에 아무것도 돌려주지 않는다

`copiesConsumed` 가 1 / 3 / 9 이라 1성 3개(3장)가 2성 1개(3장)가 되고 2성 3개(9장)가 3성 1개(9장)가 된다.
장수가 저절로 보존되므로 풀을 건드릴 이유가 없다. 기존 `카드 총량은 어떤 조작에도 변하지 않는다`
테스트가 구매 경로에서도 이 성질을 그대로 지킨다.

### 합성 결과를 세션이 아니라 결과 객체에 싣는다

`PlanningResult.Success.starUps` 로 돌려준다. 세션에 "마지막 합성"을 들고 있으면 그 다음 판매나
리롤 뒤에도 값이 남아 화면이 "2성 달성"을 두 번 띄운다.

`buy` 가 돌려주는 `unit` 은 **합성까지 끝난 뒤의 유닛**이다. 방금 산 1성이 그 자리에서 2성에
먹혔다면 그 2성을 돌려준다. 사라진 개체를 돌려주면 화면이 없는 유닛을 가리키게 된다.

### 6단계에서 아직 반영하지 않은 것

- **벤치가 꽉 차면 세 번째 장을 살 수 없다.** 원작은 "어차피 합성되니까" 예외를 두지만 명세서에
  근거가 없어 두지 않았다. 11단계 재검토 대상이다.
- 아이템은 6단계 시점에 유닛에 끼울 경로가 없어 항상 빈 목록이었다. 그래도 소모된 유닛의
  아이템을 살아남은 유닛에 3칸까지 옮기고 넘치면 가방으로 돌리도록 미리 만들어 뒀고,
  7단계에서 장착이 생기면서 실제로 그 경로가 쓰이기 시작했다.

### 테스트가 실제로 잡는지 확인한 방법

합성 규칙 여섯 군데를 일부러 고장 내고 각각 어떤 테스트가 빨개지는지 확인했다.

| 고장 낸 것 | 빨개진 테스트 |
|---|---|
| 살아남는 개체를 "보드 우선" 대신 무조건 첫 번째로 | 벤치 둘과 보드 하나 / 보드 유닛 둘 |
| 소모 순서를 보드 먼저로 | 벤치를 먼저 소모해 보드 진형을 지킨다 |
| 연쇄 합성 반복문을 1회로 | 1성 9개는 3성 / 연쇄 추적 |
| 집계 키에서 성 등급을 빼기 | 성 등급이 다르면 합성되지 않는다 / 1성 9개는 3성 |
| 3성 제외 조건을 뒤집기 | 3성은 더 이상 올라가지 않는다 |
| `buy` 가 합성 결과를 반영하지 않게 | 상점 구매 통합 테스트 3종 |

마지막 줄이 통합 테스트를 따로 쓴 이유다. 엔진만 검사하면 `buy` 와 엔진을 잇는 한 줄이 사라져도
순수 함수 테스트는 전부 초록색이다.

## 7단계에서 정한 규칙

완료 기준은 **"컴포넌트 2개 → 완성템 조합, 유닛 장착"**이다. 명세서 4-5 는 컴포넌트 9종의 이름만
정하고 나머지는 말하지 않았다. 아래가 그 빈칸을 메운 결정이다.

### 아이템 → 전투 수치 환산은 `ItemStats` 한 곳에서만 한다

아이템은 `StatType` 별 실수 증가량을 들고 있고 전투는 `UnitBuffs` 만 읽는다. 5단계에서 시너지·
아이템·증강이 전부 `UnitBuffs` 한 타입으로 모이도록 자리를 잡아 둔 덕분에, 7단계가 한 일은
`ItemStats.buffsOf` 라는 환산표 하나를 만든 것뿐이다.

**`CombatUnit.from` 이 그 함수를 직접 부른다.** 호출부가 아이템 보정을 넘기는 구조였다면 어느
호출부 하나가 빠뜨려도 전투는 멀쩡해 보인다. 같은 이유로 `CombatSimulator.setupFrom` 이
유닛을 두 번 만들던 옛 모양을 없앴다. "한 번 만들고 다시 베껴 쓰면서 `items` 를 빠뜨리는" 사고가
바로 그 모양에서 난다.

반올림은 **합계에 한 번만** 한다. 아이템마다 반올림하면 0.5 짜리 둘이 2 가 되어
"완성템 스탯 == 재료 2개의 합"이라는 `CompletedItems` 의 전제가 장착하는 순간 깨진다.

### 9종 중 둘은 일부러 전투에 닿지 않게 뒀다

| 컴포넌트 | 스탯 | 상태 |
|---|---|---|
| 힘·지혜·활력·신속·마나의흔장 | 공격력 / 주문력 / 최대 체력 / 공격속도 / 시작 마나 | 전투에 반영 |
| 수호·저항의흔장 | 방어력 / 마법저항력 | 전투에 반영 (한 풀로 합산) |
| 관통의흔장 | 치명타 확률 | **미반영** |
| 재생의흔장 | 체력 재생 | **미반영** |

- **치명타**: 4단계 전투는 난수를 한 줄도 쓰지 않는다. 폭풍의 부족처럼 정수 충전으로 바꿔야 하는데
  그건 전투 규칙을 새로 늘리는 일이고 7단계 완료 기준과 무관하다.
- **체력 재생**: 틱마다 체력을 회복시키는 장치가 전투에 아예 없다.

아무 필드에나 흘려 넣으면 "붙었다"는 착각만 만들고 11단계 밸런스가 틀린 값 위에서 돌아간다.
그래서 둘은 조용히 버려지고, `ItemStatsTest.치명타와 체력 재생은 아직 전투에 닿지 않는다` 가
그 사실 자체를 단언한다. **그 테스트가 빨개지는 날이 구현이 끝난 날이다.**

`ItemStats.targetFieldOf` 는 부르는 곳이 없는 함수다. `else` 가지가 없는 `when` 이라
`StatType` 에 값을 하나 더하면 **컴파일이 깨진다.** 그 순간 "이 스탯은 어디로 가는가"를 반드시
결정하게 만드는 덫이고, 테스트가 `buffsOf` 와 대조해 둘이 어긋나지 않게 지킨다.

### 방어력과 마법저항력은 7단계에서도 쪼개지 않았다

5단계 문서에 "7단계에서 수호의흔장과 저항의흔장이 실제로 달라야 할 때 쪼갠다"고 적어 뒀지만
쪼개지 않았다. 쪼개려면 먼저 **모든 피해에 물리/마법 종류를 붙여야** 하고, 그건 명세서 4-6 전투
규칙과 4단계 시뮬레이터를 통째로 손보는 일이다. 지금은 두 컴포넌트가 같은 값을 주므로 게임상
완전히 동등하다. 11단계 재검토 대상이고, 그때까지 `ItemStatsTest.방어력과 마법저항력은 아직 한 풀이다` 가
결정이 살아 있는지 감시한다. 그 테스트는 마스터 데이터가 아니라 **직접 만든 가짜 아이템(7 과 11)**
으로 검사하므로, 11단계에서 컴포넌트 수치를 조정해도 헛되이 빨개지지 않는다.

### 완성 아이템 45종의 고유 효과는 아직 하나도 없다

`effectId` 를 읽는 코드가 이 저장소 어디에도 없다. 명세서 4-5 는 효과 문구만 주고 수치를 주지
않아 지금 구현하면 45종이 전부 임의 값이 된다. **스탯 합산만으로 완료 기준을 만족**하므로
11단계 밸런스에서 수치와 함께 붙인다.

감시 테스트를 둘 뒀다. 하나는 `buffsOf(item)` 과 `buffsOf(item.copy(effectId = ""))` 를,
다른 하나는 그 두 경우의 **전투 결과 전체**를 비교한다. 다만 `effectId` 가 아니라 아이템 `id` 로
분기하는 구현은 이 감시가 잡지 못한다.

### 조합은 가방 안에서만, 칸 번호로 한다

- **유닛에 낀 상태로 자동 조합하지 않는다.** 자동 조합은 "컴포넌트를 둘 끼웠더니 원하지 않는
  완성템이 됐다"를 되돌릴 수 없게 만든다. 내리고(`unequip`) 합치고 다시 끼우면 된다.
- **아이템 id 가 아니라 가방 칸 번호로 고른다.** 같은 컴포넌트를 여러 개 들고 있는 것이 정상이라
  id 로 고르면 어느 것을 먹었는지 정할 수 없다.
- 검사 순서는 **칸 번호 → 같은 칸 → 조합식**이다. 잘못된 칸 번호가 "조합할 수 없다"로 보고되면
  화면이 엉뚱한 안내를 한다.
- 컴포넌트 9종의 조합 45가지가 실제로 전부 만들어지는지 테스트가 한 번에 훑는다.

### 장착 규칙

- **벤치와 보드 어느 쪽이든 끼울 수 있다.** 준비 단계에는 둘 사이를 자유롭게 오가므로 보드에만
  허용하면 올렸다 내릴 때마다 아이템이 막힌다.
- **컴포넌트도 그대로 낄 수 있다.** 칸은 아이템 **개수**를 세지 조합 단계를 보지 않는다.
- **유닛을 팔면 끼워 둔 아이템이 가방으로 돌아온다.** 유닛과 함께 사라지면 되돌릴 방법이 없다.
- 아이템이 게임 안에서 **생기는 유일한 문은 `grantItems`** 다. 10단계 크립 라운드 드랍과 9단계
  증강 보상이 전부 여기로 들어온다. 조합·장착·해제·판매는 이미 가진 것을 옮길 뿐이라 총량을
  바꾸지 않고, `아이템 총량은 조합과 장착으로 변하지 않는다` 테스트가 그 창구 하나만 밖에 두고
  나머지를 모두 검사한다.

### 7단계에서 찾았지만 고치지 않은 것

**거울전은 무승부가 아니라 적이 이긴다.** 같은 유닛 1기끼리 붙이면 마지막 틱에 서로를 죽이는데,
시뮬레이터가 유닛을 한 기씩 순서대로 처리하므로 **먼저 때린 쪽만 살아남는다.** 4단계부터 있던
성질이고 7단계가 만든 것이 아니다. 고치려면 "같은 틱에 서로 죽으면 무승부" 규칙을 새로 넣어야
하고 기존 전투 테스트가 흔들리므로 11단계 재검토 대상으로 남긴다. 대신
`ItemCombatTest.장착한 유닛이 더 세다` 는 승패가 아니라 **적에게 남은 체력이 아이템 수에 따라
단조 감소하는지**로 검사한다.

### 테스트가 실제로 잡는지 확인한 방법

7단계가 새로 만든 규칙 14군데를 일부러 고장 내고 각각 어떤 테스트가 빨개지는지 확인했다.
**14군데 전부 잡혔다.**

| 고장 낸 것 | 빨개진 테스트(대표) |
|---|---|
| 마법저항력을 방어력 풀에서 빼기 | 방어력과 마법저항력은 아직 한 풀이다 |
| 반올림을 아이템마다 하기 | 반올림은 아이템마다가 아니라 합계에 한 번만 한다 |
| 마나 스탯을 버리기 | 스탯 하나는 정확히 항목 하나로만 간다 |
| `CombatUnit.from` 이 장착 아이템을 안 읽게 | 장착한 아이템이 전투 스탯에 실제로 반영된다 |
| 시작 마나 가산 무시 / 상한 제거 | 아이템은 방어력과 시작 마나도 올린다 / 시작 마나는 스킬 소모 마나를 넘지 않는다 |
| 진영 접두어를 안 붙이기 | 진영 접두어가 붙은 개체 id 형식은 그대로다 (+ 5단계 시너지 전투 7종) |
| 판매할 때 아이템 버리기 | 유닛을 팔면 끼워 둔 아이템이 가방으로 돌아온다 |
| 장착해도 가방에서 안 빼기 | 아이템 총량은 조합과 장착으로 변하지 않는다 |
| 아이템 칸 정원 검사 제거 | 아이템 칸은 세 개까지다 |
| 같은 칸 검사를 칸 번호 검사보다 먼저 | 없는 칸을 고르면 조합 이전에 실패한다 |
| 조합해도 재료를 가방에서 안 빼기 | 컴포넌트 2개를 합치면 완성 아이템 하나가 된다 |
| 해제해도 가방에 안 넣기 | 해제하면 가방으로 돌아온다 |
| `UnitBuffs.plus` 에서 마나 보정 한 줄 빠뜨리기 | 모든 보정 항목이 빠짐없이 더해진다 |

마지막 줄이 이번에 새로 넣은 **누락 탐지 테스트**다. `UnitBuffs` 에 항목을 더하고 `plus` 에
줄을 빠뜨리면 그 항목만 조용히 0 이 되는데, 기존 테스트는 전부 통과한다. 리플렉션으로
"항목 수"와 "모든 항목이 0 이 아닌 값에서 `a + NONE == a`"를 함께 단언해 막았다.
실제로 `startingManaFlat` 을 추가할 때 이 테스트가 먼저 빨개지는 것을 확인하고 `plus` 를 고쳤다.

## 8단계에서 정한 규칙

완료 기준은 **"8인 라운드 순환 시 AI가 시너지 방향성 있게 구매"**다. 명세서 4-7 은 점수 식의
**항 이름**을 주고 숫자는 "최소 4골드는 남긴다" 하나만 준다. 아래가 그 빈칸을 메운 결정이다.

### 가중치 숫자는 `BotWeights` 한 파일에 모았다

명세서가 준 숫자는 **"항상 최소 4골드는 남기고" 하나뿐**이다(`GOLD_RESERVE`). 나머지는 전부
항 이름만 있고 값이 없어 임의로 채웠으므로, 11단계 밸런스 튜닝이 통째로 갈아엎을 자리다.
코드 여기저기에 흩어 두면 그때 무엇을 만져야 하는지 알 수 없어진다.

다만 값들 사이의 **대소 관계 하나는 명세서가 정한다.** 4-7 이 스타업을 "2성 완성 임박 시
최우선"이라고 쓰므로, 복제본 2장(`STAR_UP_PER_COPY * 2 = 12`)이 임계값 돌파 보너스(`8`)보다
커야 한다. `BotScoringTest.스타업 임박이 다른 어떤 항보다 우선한다` 가 이 관계를 지킨다.
값을 조정하더라도 이 관계는 유지해야 한다.

### "코스트 대비 현재 레벨 적정성"은 상점 확률표에서 유도했다

이 문구를 읽으려면 "레벨 L 에서 적정한 코스트"라는 표가 필요한데, 명세서에는 없다.
새 표를 만드는 대신 **이미 확정된 4-1 상점 확률표의 기댓값**을 썼다(`BotScoring.expectedCost`).
레벨 2 는 1.00, 레벨 5 는 1.79, 레벨 9 는 3.00 이 나온다. 즉 레벨 9 에서 1코스트를 집으면 -2점이다.

근거 없는 표를 하나 더 만들지 않았고, 11단계가 확률표를 바꾸면 적정 코스트도 따라 움직인다.

### 봇의 한 라운드 순서

```
0. 계획 고정   보유 태그 상위 2개. 라운드 내내 다시 계산하지 않는다.
1. 구매 루프   명세서 4-7 스코어링
2. 레벨업      보드가 정원까지 찼고 골드가 남을 때만
3. 배치        보유 유닛에서 정원만큼 다시 고른다
4. 아이템 조합
5. 아이템 장착
```

**레벨업을 구매 뒤에 둔 것은 약한 선호이지 테스트가 지키는 규칙이 아니다.** 뒤에 있으면 경험치는
"이번 상점에 살 만한 게 없어서 남은 골드"의 쓸 곳이 된다. 다만 순서를 뒤집어 8인 로비 20라운드를
다시 재 보니 차이가 작았다 — 가장 깊은 시너지 3.66 → 3.49, 최고 단계 1.74 → 1.60, 구매량은
56.5 → 54.5 로 거의 그대로였다. 방향은 지금 순서가 낫지만 이 크기를 단언하려면 밸런스 수치를
테스트에 박아야 해서 감시 테스트를 두지 않았고, 11단계에서 다시 재야 한다.

레벨업 자체에는 **보드 정원이 병목일 때만 산다**는 조건이 붙는다. 자리가 남았는데 레벨을 사는 것은
골드만 버리는 일이고, 조건이 자기 제한적이라 "라운드당 최대 몇 번" 같은 상한 표가 필요 없다.

배치는 상위 N개를 뽑는 것이 아니라 **한계 효용 그리디**다. 수호자 3명과 검사 3명 중 4칸을
개별 점수로 뽑으면 3+1 이 되어 어느 쪽도 4인을 못 채우는데, 이미 고른 유닛을 기준으로 다시 재면
4+0 이 나온다. 시너지는 조합 효과라 개별 점수로는 임계값을 맞출 수 없다.

### 판매는 자리를 만들 때만, 그것도 교체일 때만 한다

명세서 4-7 은 판매를 한 글자도 말하지 않아 처음에는 아예 넣지 않았다. 그랬더니 8인 로비를
20라운드 돌렸을 때 **모든 봇의 벤치가 9칸까지 차서 구매가 멈췄다.** 구매가 멈추면 완료 기준을
관찰하는 것 자체가 불가능하다.

그래서 "사고 싶은 카드가 있는데 벤치가 꽉 찼으면 한 장 판다"를 넣었더니, 이번에는 **봇 하나가
93장을 사고 56장을 되파는** 회전문이 됐다. 사면 팔고 팔면 사는 것이라 골드만 태우고 보유 유닛은
제자리였다.

지금 규칙은 **들어올 카드가 나갈 카드보다 나을 때만 판다**이다. 비교 기준은 판매 후보를 고를 때
쓰는 것과 같은 순서(우선 태그 일치 수 → 같은 종 보유 수 → 전투력)를 쓴다. 하나의 순서를 양쪽에
같이 써야 "이 카드가 저 카드보다 낫다"가 봇 안에서 어긋나지 않는다. 들어올 카드는 아직 개체가
없으므로 **살 경우 갖게 될 수**(보유 수 + 1)로 센다. 그래서 2성이 걸린 3장째는 벤치를 비워서라도
들어오고, 이미 여러 장 가진 종을 밀어내지 않는다.

이 가드를 넣으니 20라운드 되팔기가 봇당 55장에서 19장으로 떨어졌다. `봇이 벤치를 회전문처럼
쓰지 않는다` 테스트가 판매/구매 비 0.5 를 선으로 지킨다.

무엇을 팔고 무엇이 "낫다"인지는 `BenchEviction` 이 혼자 정한다. 처음에는 `BotBrain` 의 private
함수였는데, 그러면 상점 뽑기 결과에 기대지 않고 이 규칙만 검사할 방법이 없어 **규칙 하나가 아무
테스트에도 안 걸린 채 통과했다.** 떼어 내고 `BotBrainTest` 가 직접 찌른다.

### 리롤하지 않고, 골드가 필요해서 팔지도 않는다

둘 다 명세서 4-7 이 언급하지 않는다. "이 상점을 버릴 만한가"는 남은 풀과 목표까지의 거리를 함께
봐야 하는 별도 정책이고, 8단계 완료 기준은 **주어진 상점에서 무엇을 고르는가**로 판정된다.
`봇은 아직 리롤하지 않는다` 와 `봇의 판매는 언제나 바로 뒤의 구매를 위한 것이다` 가 이 결정을 감시한다.

### 8단계 로비는 전투를 돌리지 않는다

완료 기준의 동사가 "구매"이고, 11단계 완료 기준이 **"8인 풀 매치"**를 따로 요구한다.
전투를 붙이면 측정도 오염된다. 스코어링 봇이 이겨 연승 골드를 더 받고 그 골드로 시너지를 더
올리게 되어, "스코어링이 시너지를 만들었다"를 순환 논리 없이 증명할 수 없다.

`core/ai` 패키지에 `core.combat` import 가 한 줄도 없고, `로비를 순환해도 전투 결과는 정산되지
않는다` 가 체력과 연승 기록이 그대로인지 확인한다.

`LobbyFixture` 를 프로덕션이 아니라 **테스트 소스에 둔 것**도 같은 이유다. 진짜 `Lobby` 가 들고
있어야 할 것 — 스테이지-라운드 번호 체계, 증강/크립 라운드 삽입, 대진, 체력 정산, 탈락과 등수 —
을 8단계는 하나도 정할 수 없다. 지금 만들면 9·10·11단계가 반드시 뒤엎는다.

### 완료 기준을 무엇으로 쟀는가

**"산 카드가 그 라운드의 목표 태그와 겹치는 비율"**로 쟀다. 대조군은 점수를 한 번도 계산하지 않고
살 수 있는 **가장 왼쪽 칸부터 사는 봇**(`LeftmostBuyPolicy`)이다. 골드 규칙·레벨업·배치·아이템·
판매는 같은 `BotBrain` 이 양쪽에 똑같이 적용하므로 두 봇의 차이는 `BuyPolicy` 하나뿐이다.

좌석 편향은 미러런으로 지웠다. `nextRound` 가 "직전 상점 반납 + 새 상점 롤"을 한 함수에서 해
좌석 0 이 다른 좌석의 잔여 카드가 돌아오기 전에 뽑기 때문에, 짝수 좌석이 스코어링인 판과 홀수
좌석이 스코어링인 판을 함께 돌린다. 시드 1~5 × 미러런 2 = 봇 70명이 표본이다.

| 라운드 | 스코어링 | 대조군 | 좌석별 짝비교 |
|---|---|---|---|
| 10 | 0.47 | 0.40 | 23승 12패 |
| 20 | 0.50 | 0.38 | 29승 6패 |
| 30 | 0.51 | 0.37 | 30승 5패 |

벤치가 꽉 차 교체 판정을 거쳐 들어온 구매는 **표본에서 뺐다.** 그 판정은 `BotBrain` 이 양쪽에
똑같이 걸고 목표 태그를 보므로, 포함하면 대조군의 구매에도 방향성이 생겨 정책 차이가 흐려진다.

### 보드 시너지 깊이로는 두 봇을 구분할 수 없다 — 그리고 그게 맞다

처음에는 "발동한 시너지 단계의 합"으로 재려 했는데, **대조군이 더 높게 나왔다.** 아무거나 사서
태그를 넓게 퍼뜨리면 1단계짜리가 여러 개 켜지기 때문이다. 가장 깊은 시너지 인원으로 바꿔 봐도
20라운드에서 3.66 대 3.66 으로 같았다.

원인은 분명하다. **보드는 구매 말고도 배치와 판매가 함께 만들고, 그 둘은 대조군도 똑같이 쓴다.**
대조군은 아무거나 사지만 그중 정원만큼을 시너지 기준으로 골라 올리므로, 구매의 무작위성이
배치에서 거의 회수된다. 그래서 보드 지표는 완료 기준의 증거가 될 수 없고, 구매 자체를 재야 한다.

보드 쪽은 대신 **최소선만** 지킨다. `모든 봇이 시너지를 발동한다`(전원 1개 이상 + 보드 정원 충족),
`봇의 보드에는 2단계 이상 시너지가 하나는 선다`(봇 70명 중 과반).

### 8단계에서 찾았지만 고치지 않은 것

**계획이 방향을 이끌지 않고 따라간다.** `BotPlan` 은 보드에서 파생되므로 보드가 바뀌면 계획도
따라 바뀐다. 마지막 5라운드의 1순위 태그를 세어 보니 스코어링 봇 35명 중 18명만 한 태그를
유지했고, 오히려 대조군이 26명으로 **더 안정적**이었다. 스코어링이 임계값을 깨러 더 자주
갈아타기 때문이다. "한 번 잡은 태그는 유지" 같은 규칙을 넣지 않은 것은, 갈아타기가 이득인지
손해인지는 전투를 붙여야 잴 수 있는데 8단계 로비는 전투를 돌리지 않기 때문이다.
**잴 수 없는 규칙은 넣지 않는다**는 이 저장소의 관행대로 11단계로 넘긴다.

**명세서가 준 골드 예비량 4는 명세서 자신의 이자 규칙과 어긋난다.** 4-7 은 "항상 최소 4골드는
남기고(이자 확보)"라고 못 박는데, 4-1 이자는 10골드당 1이라 4를 남겨서는 이자가 한 푼도 붙지
않는다. 명세서 숫자이므로 그대로 넣었고(`BotWeights.GOLD_RESERVE`), 바꾸는 것은 밸런스 결정이라
11단계 재검토 대상으로 적어 둔다.

**봇은 진형을 고려하지 않는다.** 남은 빈 칸을 `HexBoard.coords` 순서대로 채운다. 근접/원거리
분리는 전투가 붙어야 좋고 나쁨을 잴 수 있다.

### 테스트가 실제로 잡는지 확인한 방법

8단계가 새로 만든 규칙을 일부러 고장 내고 각각 어떤 테스트가 빨개지는지 확인했다.
1차로 18군데를 돌려 **15군데가 잡히고 3군데가 살아남았다.** 살아남은 셋을 처리하며 규칙을 떼어내고
테스트를 더한 뒤 4군데를 추가로 돌려, 최종적으로 **22군데 중 21군데가 잡힌다.**
남은 하나는 뒤에 적은 대로 일부러 감시하지 않는 것이다.

| 고장 낸 것 | 빨개진 테스트(대표) |
|---|---|
| 우선 태그를 2개에서 1개로 | 스코어링 봇이 대조군보다 목표 태그에 맞춰 산다 |
| 우선 태그를 가장 적게 가진 것으로 | 가장 많이 보유한 태그 두 개를 고른다 |
| 시너지 겹침 항을 0으로 | 계열과 직업을 따로 센다 / 우선 태그는 가중치를 더 받는다 |
| 우선 태그 배수를 1로 | 우선 태그는 가중치를 더 받는다 |
| 임계값 돌파 보너스를 0으로 | 임계값을 새로 넘기는 유닛에만 보너스가 붙는다 |
| 스타업 항을 0으로 | 같은 유닛을 가질수록 스타업 항이 커진다 |
| 골드 예비 4를 0으로 | 사고 나서 최소 골드가 남지 않으면 감당 불가다 |
| 레벨 적정성 항을 0으로 | 적정 코스트에서 멀수록 점수가 깎인다 |
| 초반 예외 제거 | 초반에는 태그를 보지 않고 코스트 대비 스탯만 본다 |
| 구매 하한선 제거 | 스코어링 봇이 대조군보다 목표 태그에 맞춰 산다 |
| 정책이 하한선을 무시 | 스코어링 봇이 대조군보다 목표 태그에 맞춰 산다 |
| 교체 가드 제거 | 봇이 벤치를 회전문처럼 쓰지 않는다 |
| 자리용 판매 제거 | 봇의 보드에는 2단계 이상 시너지가 하나는 선다 |
| 살 게 없으면 리롤하게 | 봇은 아직 리롤하지 않는다 |
| 배치를 한계 효용 대신 개별 점수로 | 봇의 보드에는 2단계 이상 시너지가 하나는 선다 |
| 레벨업의 보드 정원 조건 제거 | 보드에 빈 자리가 남아 있으면 레벨을 사지 않는다 |
| 판매 후보의 보유 수 키 제거 | 2성 직전 카드는 남기고 약한 한 장짜리를 내보낸다 |
| 판매 후보의 우선 태그 키 제거 | 우선 태그를 가진 카드는 보유 수가 적어도 남긴다 |
| 교체 판정의 보유 수 조건 제거 | 2성이 걸린 세 장째는 벤치를 비워서라도 들인다 |
| 교체 판정의 우선 태그 조건 제거 | 우선 태그 카드는 보유 수가 적어도 벤치를 비우고 들어온다 |
| 교체 판정을 항상 참으로 | 더 나쁜 카드를 들이려고 벤치를 비우지는 않는다 |

### 1차에서 살아남은 셋과 그 처리

**① 레벨업의 보드 정원 조건**과 **② 판매 후보의 "같은 종 보유 수" 키**는 고장 내도 307개가 전부
초록색이었다. 로비 테스트가 20라운드를 돌린 **결과**만 보기 때문이다. 한 번의 판단이 달라져도
벤치에 쌓인 여유분이 흡수해 최종 보드가 거의 같아진다.

그래서 `BenchEviction` 을 `BotBrain` 에서 떼어 내고 `BotBrainTest` 9종을 새로 썼다. 상점 뽑기와
무관하게 규칙 하나씩을 직접 찌른다. 다시 돌리니 둘 다 잡힌다.

그 재검증이 **허술한 테스트도 하나 잡아냈다.** `우선 태그를 가진 카드는 마지막까지 남긴다` 는
우선 태그 카드에 보유 수까지 유리하게 줘 놓아, 우선 태그 키를 통째로 없애도 통과했다.
조건을 뒤집어 태그 없는 카드 쪽에 유리하게 바꾸니 그제야 빨개진다. 테스트를 쓸 때는 **검사하려는
키가 유일한 이유가 되도록** 나머지 키를 반대로 걸어야 한다.

**③ 레벨업과 구매의 순서**는 감시 테스트를 **일부러 두지 않았다.** 위에 적은 대로 실제 차이가
작아서, 단언하려면 밸런스 수치를 테스트에 박아야 한다. 11단계가 그 수치를 바꾸면 테스트가
거짓으로 빨개질 것이다. 대신 무엇을 쟀고 얼마가 나왔는지를 코드 주석과 이 문서에 남겼다.

  `EXP_TO_NEXT_LEVEL` 이 그 값이고, 누적값이 필요하면 `cumulativeExpToLevel(level)` 을 쓴다.
